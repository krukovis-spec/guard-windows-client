# Проверка настоящей службы в disposable VM

Это тест M0/M3, **не installer v2 для семьи и не проверка M1**. Он нужен до полноценного мастера установки: впервые проверить настоящий SCM/LocalSystem, системное хранилище, административный pipe, снятие одноразового startup flag и сохранение identity после обычного перезапуска службы.

## Границы

- Единственная цель: `GuardV2-Lab-20260930`, VM ID `8f088b63-9193-4ecc-bb20-415ef11fd4c8`, BIOS UUID `236ea6ef-9cc6-4295-9934-6f7497f9d262`, 80 GB-диск внутри `%LOCALAPPDATA%\GuardV2Lab\VM\Virtual Hard Disks`, Gen2/Secure Boot/vTPM. Внутри снова проверяются UUID, Hyper-V manufacturer/model, имя не совпадает с хостом и elevated administrator.
- На хосте только Hyper-V/PowerShell Direct, публикация временного пакета и результат в `GuardV2Lab\Access`. Права администратора нужны для Hyper-V. Служба Guard, политики, firewall, hosts и аккаунты хоста не изменяются. Не перезапускает хост и не включает выключенную VM автоматически.
- Отказывается перезаписывать существующую службу `Guard`, папки Guard в Program Files/ProgramData. Наличие защищённой папки проверяется через её доступного родителя, а не интерпретируется как отсутствие при запрете чтения самой папки.
- По умолчанию пакет содержит test-only origin `https://guard-lab.invalid` и фиктивный публичный signer pin. Опциональный проверенный manifest Android-пилота закрепляет настоящий Guard origin и публичный сертификат APK. Ни сетевого профиля/привязки, ни административного relay-токена, ни приватного телефонного ключа здесь нет; сам origin не включает транспорт. Пакет никогда не применяется как семейный release.
- До любых гостевых изменений создаётся новый снимок текущего состояния. После теста, включая ошибку, выполняются мягкое выключение только закреплённой VM, восстановление **этого** снимка, загрузка и проверка отсутствия новых Guard-файлов/службы. Только после подтверждения восстановления тестовый снимок удаляется; исходный `clean-windows-20260930` не удаляется. При неудаче recovery скрипт сообщает FAIL и сохраняет снимок; принудительного выключения нет.

## Запуск

1. Обычный терминал: `scripts/lab/Build-ServiceLabPackage.ps1`. Он публикует self-contained service/probe в новую папку `%TEMP%\GuardServiceLab-<guid>`, создаёт manifest всех файлов и возвращает путь/его SHA256. Не запускает Guard. `win-x64` restore может обновить RID-раздел существующего NuGet lock; версии зависимостей не меняются.
2. После проверки безопасности и подтверждения UAC запустить `Invoke-ServiceBootstrapLab.ps1 -PackageRoot <этот-путь> -ManifestSha256 <этот-хеш>` в повышенном PowerShell. Секреты не передаются аргументами: используется уже сохранённая user-DPAPI гостевая учётная запись из `Access\guest-credential.xml`; пароль не выводится и не сохраняется повторно. Нет очереди произвольных повышенных команд.
3. Проверить **новый** `Access\service-bootstrap-<runId>.json`: нужны `Status=PASS`, `Experiment.Status=PASS`, одинаковые descriptor SHA256 до/после рестарта и `SnapshotRecovery=BOOT_VERIFIED`. Код процесса тоже должен быть 0. Старые отчёты/тайм-аут наблюдения не доказывают завершение; проверять исходный процесс.
4. После завершения удалить только собственную проверенную временную папку пакета; не удалять чужие файлы/VM/основной recovery snapshot. При отменённом UAC гостевые изменения не начинаются, отчёт эксперимента не создаётся.

Для проверки согласованных pins: `Build-ServiceLabPackage.ps1 -AndroidPilotManifest <полный-путь-к-pilot-manifest.json> -AndroidPilotManifestSha256 <SHA256-этого-файла>`. До publish проверяются commitment manifest, точный Guard origin/package/version, хеш APK и SHA256 публичного DER. Приватное хранилище подписи не требуется. Получившийся service/probe manifest сохраняет публичные pins; guest проверяет origin через настоящий authenticated descriptor. При отсутствии дополнительных аргументов прежний синтетический сценарий не меняется. Никакой такой запуск не выдаёт телефонных полномочий и не принимает M1.

Guest сначала проверяет pinned manifest и каждый файл; потом создаёт normal own-process automatic LocalSystem service с одноразовым initialization flag. `WaitNamedPipe` здесь только ждёт появления endpoint; **аутентификацию** выполняет настоящий `GuardSetupQueryClient`. При наличии bootstrap flag клиент обязан отказать. После stop/изменения SCM path/normal start тот же клиент и `SetupInspection` проверяют состояние/ACL и public export; второй normal restart обязан сохранить точное описание. Оба `inspect` также требуют `Readiness.ServiceBoundary=Satisfied` и выводят `serviceConfiguration=OBSERVED`: это реальное query-only чтение SCM внутри службы, а не прежняя заглушка Unknown. Общая готовность должна оставаться false; service DACL и действующие блокировки этим не доказываются.

Смена `PathName` использует CIM, а не fragile nested quotes в `sc.exe` под Windows PowerShell 5.1. Другие настройки/права/политики не меняются. У лабораторной регистрации обычный service DACL: это не защита от остановки администратором, не M8 и не повод показывать Protected.

## Безопасные проверки без VM

`scripts/lab/Test-LabSafety.ps1` парсит все скрипты и проверяет отказ guest-скриптов на хосте **до установки/доступа к пакетам**. Обычный `Guard.Windows.Ipc.Tests` не включает live-mode. Только явный `--installed-service-lab inspect|reject-bootstrap` включает read-only проверку установленной службы, дополнительно требуя имя лабораторного guest и elevated administrator; по умолчанию safe suite остаётся прежней. При запуске этого режима на хосте ожидается exit 1 до IPC.

На 05.10.2026: настоящий bootstrap → отказ клиента при одноразовом SCM flag → normal start → authenticated inspection/export → normal restart прошёл **PASS**, exit 0. Отчёт `Access\service-bootstrap-72b78629cacc40bfbfaac73a0a0373b2.json`, 15:23 UTC: SYSTEM-only ProgramData, наблюдаемая конфигурация службы, одинаковый descriptor SHA256 до/после рестарта; общая готовность остаётся false. `SnapshotRecovery=BOOT_VERIFIED`, собственный тестовый снимок удалён, исходный recovery сохранён. Пакет — 442 файла. Экран WPF, диалог сохранения, камера, реальная биометрия, полный Windows reboot с установленной службой и M1 остаются отдельными gates.

07.10.2026 пакет с настоящим origin и постоянным Android signer прошёл **новый VM PASS**, actual elevated child exit 0. Отчёт `Access\service-bootstrap-560dcec11ca148f39f8776114ddd2ea7.json`, 08:49:44 UTC: bootstrap endpoint отклонён, authenticated SYSTEM/ACL/SCM inspection PASS; descriptor SHA256 до/после рестарта одинаков (`9EFD7741F400596003409B4C96E8CC02C092B8FC760B6E201DBA336985EA0E2A`). Готовность false, policy writes false. `SnapshotRecovery=BOOT_VERIFIED`, собственный снимок удалён, VM снова чистая. Manifest пакета `00EECE81FEA40E7D0AE4B8D65C50927849DB985B8390065CD8C53E4870A9BCCE`; первоначальная отмена UAC была до запуска, повтор использовал тот же проверенный пакет. Это проверка службы с согласованными pins, не сетевой привязки/биометрии/защиты. На host служба не устанавливалась.

Ошибки, найденные настоящим прогоном и исправленные:

- После production checkpoint нужен новый PowerShell Direct session и повторная проверка чистоты guest до записи. Текущий AVHDX читается из текущего CIM setting: Hyper-V wrapper в первом recovery удерживал старый путь после restore. После ограниченного ручного восстановления первый guest загрузился чистым; дальнейшие восстановления выполнялись автоматически.
- `dotnet publish` переносил атрибут Pinned (524288), который Windows PowerShell 5.1 Direct не десериализует. Только новая временная копия нормализуется к Archive до manifest; исходники/байты не меняются. Скрытый ProgramData проверяется с `Get-Item -Force`.
- SYSTEM-only DACL не задаёт SYSTEM-владельца файла: у LocalSystem default owner оказался Administrators. Перед созданием host/workers служба теперь задаёт своему process token `TokenOwner=SYSTEM`, затем проверяет результат. Нет impersonation, изменения привилегий или принятия существующих небезопасных файлов; прежние ACL-отказы сохранены. [Модель владельца Windows](https://learn.microsoft.com/en-us/windows/win32/secauthz/owner-of-a-new-object).
- SCM возвращает специальное имя `LocalSystem`, которое обычный `NTAccount.Translate` не распознаёт. Только этот точный SCM alias теперь отображается в SYSTEM SID; остальные имена проходят прежний lookup. Регрессионный тест с настоящим classifier сначала воспроизвёл отказ, затем прошёл. [Описание Microsoft](https://learn.microsoft.com/en-us/windows/win32/services/localsystem-account).

При отказе отчёт содержит ограниченные типы/методы исключений, этап и булевы ACL/readiness-факты, а не raw event payload, файлы состояния, ключи или пароли.

Основа маршрута: [Microsoft PowerShell Direct](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/powershell-direct), [WaitNamedPipe](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-waitnamedpipew), [CIM Win32_Service.Change](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/change-method-in-class-win32-service).
