# Guard — родитель для Android

Это незавершённый компонент Guard v2. Главный экран открывает русский экран привязки компьютера: камера QR, проверка компьютера, защищённые ключи, биометрия, обмен и полный код сравнения. После подтверждённой привязки доступны импорт профиля, чтение проверенных запросов, сохранение выбранного решения после биометрии и отдельная отправка сохранённой подписи в relay. Получение и применение решения установленной Windows-службой и проверка квитанции в экране пока не подключены. Настроенный выпуск и проверка настоящим телефоном ещё не выполнены — это не готовый семейный клиент.

## Экран привязки — 2026-10-01

### Доступ к relay после привязки

`AndroidEnrollmentCeremony.importNativeProfile/openNativeProfile` теперь соединяет проверенную завершённую привязку и прежние Keystore-ключи с профилем `.guard-native` от off-PC `export-native`. Профиль расшифровывается только decryption key этого телефона и содержит только отдельный approval credential. Origin/mailbox/device/authority берутся из уже сохранённого GREO/GREC, не из чужого файла. Требуется полный SHA-256, полученный **независимо** с экрана родительского оператора; нельзя вычислять ожидаемое значение из того же файла или брать его из relay. Сам профиль не удостоверяет отправителя, не назначает владельца и не подписывает разрешения.

На диске `noBackupFilesDir/native-transport` хранится только шифротекст с проверенным commitment и временем импорта. Ранее установленный доступ не заменяется: повтор тех же plaintext-данных ничего не пишет; другой ключ/credential/срок, повреждение, истечение или откат часов — отказ. API повторно проверяет подписанное подтверждение привязки, compiled origin и сохранённые ключи, не создаёт новые. Расшифрованный объект нужно закрывать после использования; управление текущими epochs/отзывом остаётся задачей runtime, не исторического proof.

В подтверждённой привязке теперь есть «Настроить обмен с компьютером». Для инженерной настройки:

1. Сохранить на телефон только `.guard-native` от `export-native`, не приватные `.job`. Ввести все 64 символа SHA-256 с отдельного доверенного родительского компьютера, не из сообщения с файлом.
2. Нажать «Выбрать файл профиля» и выбрать загруженный файл через системное окно. Приложение принимает только `content:` и целый обычный локальный файл размером 233 байта; потоковые/cloud-provider файлы сначала скачать. Расширение, имя и сообщаемый MIME не доказывают формат или подлинность.
3. После импорта приложение повторно открывает сохранённый шифротекст и показывает его срок. Это не проверка сети/актуальных прав и не разрешение запуска. Уже сохранённый профиль можно проверить, но нельзя заменить или сбросить этим экраном.

Выбор и checksum остаются только в памяти текущей Activity. После пересоздания экрана старый результат не импортируется; нужно повторить действие. Обычный возврат из системного picker ждёт видимый экран до пяти секунд. URI не сохраняется, постоянное разрешение чтения не запрашивается. Чтение ограничено 234 байтами и ожиданием 20 секунд, отмена закрывает поток и вызывает `CancellationSignal`; поздний результат не записывается. Некорректный provider может не завершить свой Binder-вызов: один незавершённый вызов на процесс блокирует повторное чтение, а не накапливает workers. Перед атомарной записью ещё раз проверяется отмена. После уже завершённой записи уход с экрана её не откатывает — фактическое состояние перечитывается.

Использованы существующий AndroidX [Activity Result API](https://developer.android.com/training/basics/intents/result) и [ContentResolver](https://developer.android.com/reference/android/content/ContentResolver); новых пакетов/разрешений нет. `ux-copy` применён к русским названиям действий, состояниям отмены и ошибкам без ложной готовности защиты. Итоговый Codex-подобный стиль остаётся отдельным M7 после функциональности.

55 JVM-тестов, debug APK, instrumentation APK и lint (0 ошибок, 13 прежних предупреждений) проходят локально. Включены фактический .NET→Kotlin HPKE-файл, каждое изменение байта/усечение, неправильные hash/recipient/time, hostile plaintext, повтор/restart, отказ замены/повреждения, expiry/отмена перед записью, короткие чтения/EOF/лишние байты/zero-progress. Реальный picker, поворот/перезапуск Activity, отмена зависшего provider, доступность и биометрия **ещё не проверены на телефоне**; основной approval runtime также не подключён. Формат — [протокол](../../protocol/guard-relay-v1.md), команды — [оператор](../../tools/Guard.Provisioning/README.md).

### Чтение запросов — 2026-10-01

В подтверждённой привязке открыть «Посмотреть запросы компьютера». Нужен ранее импортированный действующий профиль. Экран делает один GET к закреплённому relay, проверяет всю порцию и показывает полные идентификаторы, сведения компьютера, комментарии и указанные сроки. Следующая порция загружается отдельной кнопкой; «Проверить с начала» начинает чтение заново. При ошибке старые карточки очищаются. Имена/комментарии — данные с компьютера, не доказательство безопасного приложения; невидимые управляющие/bidi-символы показаны как `\u{...}`.

`AndroidEnrollmentCeremony.openNativeInbox` выводит origin/mailbox/оба ключа/device epochs только из перепроверенной завершённой привязки и существующих Keystore-ключей; secrets не принимает из intent/ссылки. Один одноразовый сеанс использует профиль только в памяти и закрывает его после чтения. `NativeRequestInbox` проверяет ключи до отправки и после проверки данных, время/отмену — также после потенциально долгой проверки ключей непосредственно перед HTTP. Никаких redirects/proxy/ambient cookies; отмена и 20-секундный deadline отключают соединение. Заголовки и фактическое чтение ограничены ожидаемым типом/encoding и размером тела; максимум 16 frames/порция. Parser принимает строгую ограниченную форму JSON, которую выдаёт текущий Worker, с canonical base64 и JS-safe монотонными cursors; неизвестные/дублирующиеся поля, комментарии и экранированные псевдонимы не принимаются. Не доверяет MIME/HTTP success/nextCursor как праву на действие.

Каждый GRF1 расшифровывается существующим HPKE и проверяется подписью компьютера, exact recipient/mailbox/device/epochs и сроками. Сроки перепроверяются после всей порции. Квитанции также проверяются, но без привязки к сохранённой команде не показываются как «применено». Сам poll остаётся read-only: нет публикации, durable cursor или `/ack`, чтение не удаляет сообщения и не теряет квитанцию. Для отдельного решения сохраняется неизменный исходный зашифрованный frame; getter snapshot возвращает независимую копию. Отображённый запрос может уже измениться на компьютере — применение обязан подтвердить сам компьютер.

Локально: 62 JVM-теста, debug/instrumentation APK и lint 0 ошибок/13 прежних предупреждений PASS. Новый набор использует настоящий .NET ciphertext и реальные JCA/HPKE-подписи при управляемом HTTP; проверены неверные schema/base64/recipient/cursors, подмена подписи/epochs, время, receipt без решения, размер/тип/редирект, отмена при чтении и во время локальной проверки ключей, настоящий coroutine deadline с виртуальным временем. Исправлены compile-time inference/import конфликты; проверки безопасности не ослаблялись. Реальные Cloudflare/телефон/экран/Keystore здесь не запускались. Дальше — явный выбор, свежий CryptoObject, durable signed outbox, согласованное выделение wire-cursor для общего device inbox, доставка и точная квитанция. Этот список не является приёмкой M4.

### Подписать и сохранить решение — 2026-10-01

1. В запросе нажать «Выбрать решение». Приложение заново проверяет исходный frame, подтверждённую привязку, ключи и профиль. Если уже есть ожидающее решение, показывает его вместо нового подтверждения.
2. Явно выбрать один из четырёх вариантов: постоянно, на время, дневной лимит или отказ. Для времени/лимита нужны 1–1440 минут. «Проверить выбранное решение» показывает полный запрос и выбранные условия; поле ввода уже не меняет решение.
3. Нажать «Подписать решение биометрией». Только свежий `BIOMETRIC_STRONG`, TYPE_BIOMETRIC и та же per-operation Signature. Операция заранее фиксирует snapshot hash/challenge, exact target/revision/epochs, choice, sequence из outbox, случайные command/nonce и срок подписи (не больше 15 минут, срока запроса/frame/профиля). После callback и перед atomic commit повторяются проверки ключей/доверия/времени/отмены. Подмена Signature, повтор callback или уход с экрана не переиспользуют подтверждение.
4. «Решение подписано и сохранено» означает только атомарную запись точных bytes в `noBackupFilesDir/approvals`. Через «Сохранённое решение» можно открыть ту же запись после перезапуска. Подпись сама по себе не меняет доступ. До точной терминальной квитанции новое решение не подписывается — даже если сохранённая подпись истекла. Ошибка после commit/потеря UI-результата не удаляет запись и не создаёт подпись повторно.

68 JVM-тестов, debug/instrumentation APK и lint 0 ошибок/13 прежних предупреждений PASS. Новые проверки используют реальный .NET frame/JCA и временные атомарные файлы: четыре выбора, immutable data, wrong/repeated callback, отмена/expiry/clock rollback/смена доверия до подписи и непосредственно перед commit, конкурирующее решение и повторное открытие. Существующие три Kotlin→.NET interop проверки проходят. Физический отпечаток/lifecycle/power loss не проверены; это не проверка отзыва authority на сервере, TPM-часов или защиты от root. Дальше нужны согласованный общий device-recipient cursor, доставка exact bytes, matching receipt и подтверждённый Windows effect. M1/M4 остаются открыты; визуальный проход — M7.

### Отправить сохранённое решение — 2026-10-01

В «Сохранённом решении» нажать «Отправить сохранённое решение». Свежая биометрия не нужна: отправляется уже подписанное неизменное решение. Успех означает только «Сервер принял сообщение», не разрешение доступа. При потере ответа повторяется та же подпись; до терминальной квитанции запись не удаляется. Нужны действующий профиль и Worker с `/frames/reserve` — этот API ещё не загружен в production, локальный маршрут проверен управляемым HTTPS.

`NativeApprovalDelivery` сначала атомарно сохраняет exact reservation input, затем получает общий recipient cursor, создаёт и сохраняет exact HPKE/GRF1 перед публикацией. GOB2 объединяет прежний GRAP и transport metadata в одном файле; GOB1 читается и мигрирует только при следующей успешной записи. После обрыва/restart sealed frame повторяется побайтно, даже после lease expiry: сервер мог уже принять/ack-нуть его. Только точный ответ о просроченном/отсутствующем резерве (или отсутствующей старой reservation с неверным временем) допускает один новый outer frame за действие, с тем же GRAP/sequence. Неизвестный ответ сохраняет исходное состояние. Истечение всего frame/profile не сбрасывает очередь; требует восстановления/квитанции, а не новой подписи.

Нет redirects/proxy/cookies, скрытого фонового отправителя, подписи или `/ack`; fixed origin/recipient берутся из confirmed enrollment. Проверки ключей, exact pending/CAS, времени и отмены идут перед dispatch и atomic commit; 20s deadline отключает HTTP, ответ ограничен 1024 bytes/schema/content type. Время проверяется и после медленных проверок; это не аппаратная защита от clock rollback/root. Receipt consumption/runtime/отзыв authority/реальное Windows effect остаются следующими gates. Сохранённый published flag не доказывает Applied.

78 JVM-тестов, debug/instrumentation APK, lint 0 ошибок/13 прежних предупреждений PASS; свежая Release-сборка/29 v2 harnesses/45 legacy checks PASS. Новый `--verify-android-approval-frame` в .NET расшифровывает созданный Android frame и проверяет exact GRAP, подпись, enrollment/request binding и разделение HPKE domains. Тесты используют только публичные тестовые ключи, реальные JCA/HPKE и временные файлы. Покрыты потерянные reservation/POST-ответы, restart, конкурирующий ciphertext, отказ commit, expiry, schema/headers/размер, повреждение/migration/CAS, отмена при проверке ключей и timeout. Настоящий телефон/Keystore/отпечаток/power loss/Cloudflare/VM этим прогоном не проверялись. M1/M4 не приняты; Codex-стиль остаётся M7.

### Привязка через QR

`EnrollmentActivity` доступна только из приложения (`exported=false`), не принимает QR из intent, ссылок или буфера обмена. Адрес сервера берётся только из публичной release-настройки Gradle `guardEnrollmentRelay`, с проверкой канонического HTTPS при сборке и повторной проверкой QR. Без неё стандартная сборка показывает понятное сообщение и не открывает сканер; тестовый адрес в релиз автоматически не подставляется. Этот pin должен совпадать с проверенным endpoint выпуска Windows. Он не является секретом или разрешением доверять произвольному серверу.

Для настроенной инженерной сборки путь такой:

1. «Привязка компьютера» → «Сканировать QR-код компьютера». Сканировать только код из открытой локальной настройки нужного компьютера, не присланное изображение. После сканирования проверить компьютер и нажать «Это мой компьютер — продолжить».
2. Нажать «Подтвердить биометрией». Только `BIOMETRIC_STRONG` и точный `CryptoObject.Signature`; кода телефона как замены нет. После сохранения подписи обмен начинается автоматически. Оставить открытыми экран телефона и окно настройки Guard на компьютере. Биометрия автоматически не повторяется.
3. Когда компьютер проверит ключ, сравнить **все восемь строк** кода на обоих экранах и явно подтвердить совпадение в Windows. Подписанный результат появится на телефоне автоматически. «Проверить сейчас» возобновляет проверку без создания новых ключей. HTTP success, загрузка подписи и короткий код не означают завершение привязки.

Ожидание принадлежит только открытому экрану (`onResume`/`onPause`), не фоновой службе: последовательные ограниченные обмены каждые 2 секунды, для остановленных/истёкших попыток — только сверка раз в 10 секунд. После сетевых ошибок пауза растёт до 30 секунд; сообщение объясняет повтор, а не утверждает успех. Ошибки хранилища/ключей/проверки подписи не превращаются в сетевой цикл. Ручное действие сначала отменяет и дожидается текущей coroutine; уход с экрана отменяет обмен. Обычный возврат перечитывает текущую сохранённую попытку; после пересоздания Activity её можно открыть из списка. При неизменном этапе экран не перестраивается, чтобы не сбивать прокрутку и доступный фокус во время сравнения.

Экран скрыт в снимках/недавних приложениях, скрывает сторонние overlay-окна и фильтрует перекрытые нажатия. При уходе с экрана текущий biometric operation отменяется; новая Activity не получает старый callback как право подписи. Секрет сканирования не сохраняется в Bundle/clipboard/файл. После обычного возврата из отдельного окна сканера обработка ждёт видимую Activity не более пяти секунд. После остановки/поворота экрана привязка читается заново из no-backup хранилища; исходный QR может понадобиться снова. Конкретные lifecycle/камера/overlay/биометрия ещё требуют физической проверки.

Сканер — официальный [Google Code Scanner 16.1.0](https://developers.google.com/ml-kit/vision/barcode-scanning/code-scanner), без собственной камеры и разрешения CAMERA. Нужны Google Play services и загруженный scanner module; для его первой загрузки может потребоваться интернет. В проект добавлен один прямой пакет; 32 новых артефакта его транзитивных зависимостей проверены повторным HTTPS-чтением из Google Maven, SHA256 закреплены в `gradle/verification-metadata.xml`, все 722 старые записи сохранены без изменения хешей. Проверка зависимостей не отключалась. Это не самостоятельный облачный аккаунт/deploy.

Проверки: 47 JVM-тестов, debug APK, instrumentation APK и lint (0 ошибок, 13 прежних предупреждений). Виртуальное время проверяет интервалы/сброс backoff, timeout, отмену и отсутствие обновлений после закрытия, остановку на подтверждении/retention и отказ от повторов при ошибках целостности/хранилища. Ранее проверены malformed release pin и публичный синтетический pin; текущая стандартная сборка по-прежнему без pin. .NET проверяет свежие Kotlin offer/claim/signature/MAC/capability и реальные HPKE claim/proof/query. Это реальные локальные файлы/JCA и coroutine-тесты, но **не** физическая камера/биометрия/attestation, Android lifecycle на устройстве или принятие связанного Windows→relay→телефон сценария. Recovery Kit, доверенная выдача view-key PWA, отзыв/очистка старых записей, Windows setup UI и финальное оформление M7 остаются открыты.

Минимальная версия для текущего криптографического маршрута — Android 12 (API 31): аппаратный ECDH-ключ использует `KeyProperties.PURPOSE_AGREE_KEY`, которого нет в API 30. Совместимость и сильный отпечаток конкретного телефона родителя ещё должны быть проверены физически; программный ключ или PIN не подставляются автоматически.

Проверка 2026-09-24: прежняя ошибка `ByteArray.ifEmpty` исправлена; 18 JVM-тестов и сборка debug APK проходят. Реальные зашифрованные запрос и квитанции .NET проверяются без подставного verifier; подпись решения Kotlin/JCA независимо проверяется .NET. Общий вектор `protocol/test-vectors/relay-exchange-v1.properties` содержит только публичные тестовые ключи и никогда не используется приложением.

`FileApprovalOutbox` сохраняет точные подписанные байты и номер решения атомарно. Создавать его можно только в `Context.noBackupFilesDir`, одним процессом приложения. Подписанная промежуточная квитанция не снимает ожидание; терминальная квитанция должна совпадать с точным решением. Проверены повторное открытие, конфликт параллельной записи, повреждение файла и повтор квитанции. Реальный crash/power-loss ещё не проверен. Повторная обычная привязка не перезаписывает существующий ключ родителя.

## Незавершённая привязка — 2026-10-01

`AndroidEnrollmentCeremony` сохраняет исходный offer в `noBackupFilesDir/enrollment` **до** создания раздельных Keystore-ключей. Имена зависят от полного хеша offer; старый общий ключ не перезаписывается и не удаляется. После сбоя до сохранения claim нужен тот же QR; после сохранения claim повторное сканирование не требуется. Подпись из свежего biometric CryptoObject сначала атомарно сохраняется вместе с точными claim/chain/MAC, затем может быть отправлена. Повторная отправка использует ту же подпись. Сам QR-секрет и его hash-key на диск не записываются.

Потерянный ключ после сохранения claim не создаётся заново; несовпадение ключа, срока, callback, повреждение файла и откат ниже сохранённого времени останавливают попытку. Это не защищённые аппаратные часы: Windows остаётся окончательной проверяющей стороной. Локальная отмена сохраняет запись и ключи, потому что компьютер мог уже завершить привязку; она **не означает отзыв на Windows**. До безопасной очистки/отзыва хранится максимум восемь попыток, без автоматического удаления истёкших. Это открытый lifecycle gate, не готовый пользовательский сценарий.

Keystore повторяет генерацию в TEE только при `StrongBoxUnavailableException` и отсутствии частично созданного ключа. Остальные ошибки не маскируются. Проверяются hardware/profile обоих ключей; для подписания требуется per-operation strong biometric без PIN. По [Android KeyInfo](https://developer.android.com/reference/android/security/keystore/KeyInfo#getUserAuthenticationValidityDurationSeconds()) этот режим читается как `-1`, хотя задаётся builder-значением `0`. Проверка Google chain, challenge и APK identity выполняется отдельно на Windows.

Локальные lifecycle-проверки на предыдущем этапе: 41 JVM-тест, debug APK; `lintDebug` (0 ошибок, 13 прежних предупреждений) и `assembleDebugAndroidTest`. Физический `RealDeviceSecurityTest.hardwareProfilesAndRestartKeepSameKeys` больше не пустой: создаёт два уникальных тестовых alias, проверяет неизменность ключей и отказ подписи без биометрии, затем удаляет только их. Он **ещё не запускался на телефоне** и не заменяет успешный интерактивный отпечаток, его отмену/смену и проверку chain вне телефона. Ceremony теперь подключена к экрану/scanner выше; связанный Windows setup и физическая проверка ещё впереди.

`EnrollmentExchange` шифрует claim/chain, proof и запрос состояния; ответ Windows отдельно подписан. GEN2 того же no-backup файла сохраняет scoped relay capability (не QR secret/proof key), точные sealed bytes/nonce до отправки и проверенный ответ вместе с погашением ожидаемого запроса. Повтор использует прежние bytes, после минуты — новый nonce. Подмена/регрессия версии или стадии и expiry до/после fsync отказывают. GEN1 читается без потери ключей; отсутствующая capability требует того же живого QR, а после срока — recovery, не сброса.

`AndroidEnrollmentCeremony.synchronize` выполняет один HTTPS POST/GET через `HttpsURLConnection`: закреплённый offer endpoint, без redirects/proxy/cache/ambient cookies, общий timeout 20 секунд с disconnect при отмене, ответ максимум 414 байт. HTTP success/204 не подтверждают владельца. После expiry/локальной отмены разрешён только query в пределах 24 часов relay retention; ключи не удаляются. `confirmedEnrollment` повторно проверяет сохранённую подпись в момент её первоначального принятия и существующие Keystore-ключи, поэтому минутный срок ответа не уничтожает привязку после restart. Это доказательство **исторически завершённой привязки**, не актуальных полномочий, Recovery Kit или готовности защиты. Отзыв/epoch lifecycle должен проверяться отдельно при каждой операции.

Проверены реальные файлы/JCA, три последовательные стадии, потерянный/повторный ответ, clock rollback, expiry перед atomic move, миграция GEN1 и bounded/cancelled HTTP на управляемых соединениях. Межъязыковая криптография .NET↔Kotlin проходит; реальный сетевой путь Windows→relay→телефон ещё не принят. Экран Android теперь вызывает этот транспорт; внешнего deploy нет.

Безопасная проверка из корня репозитория (JDK 17 и Android SDK должны быть установлены):

```powershell
$env:JAVA_HOME='C:\Users\kruko\AppData\Local\GuardDev\jdk-17.0.19+10'
$env:ANDROID_HOME='C:\Users\kruko\AppData\Local\Android\Sdk'
Push-Location parent/android
.\gradlew.bat :app:testDebugUnitTest :app:assembleDebug --offline --console=plain
Pop-Location
dotnet run --project tests/Guard.Windows.RelayCrypto.Tests -c Release --no-launch-profile
dotnet run --project tests/Guard.Windows.RelayCrypto.Tests -c Release --no-launch-profile -- --verify-android parent/android/app/build/test-interop/android-approval.hex
dotnet run --project tests/Guard.Windows.RelayCrypto.Tests -c Release --no-launch-profile -- --verify-android-enrollment parent/android/app/build/test-interop/android-enrollment.txt
dotnet run --project tests/Guard.Windows.Crypto.Tests -c Release --no-launch-profile -- --verify-android-exchange parent/android/app/build/test-interop/android-enrollment-exchange.txt
```

Debug APK создаётся в `app/build/outputs/apk/debug/app-debug.apk`. Это не готовый клиент управления защитой; он не устанавливался на телефон. Аппаратная подпись через `BIOMETRIC_STRONG`, подключение сети и регистрация доверия должны быть проверены в связанном сценарии.

До пилота обязательны проверка аппаратного хранения ключа, сильной биометрии без кода телефона, отзыва ключа при добавлении отпечатка и восстановления очереди подтверждений на реальном устройстве. Полная русская инструкция и статус проекта: [README](../../README.md).
