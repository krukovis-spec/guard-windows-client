# Guard Relay v1

The relay is an untrusted HTTPS poll/store-forward mailbox. It cannot decide policy, decrypt inner content, mint approvals, or advance a parent sequence. Per parent key, endpoints use stop-and-wait: no sequence `n + 1` before a signed terminal receipt for `n`.

All messages use strict UTF-8, big-endian integers, version 1, bounded lengths, and reject unknown enums, trailing bytes, malformed lengths, invalid timestamps and oversized data. `RequestSnapshot` (`GRRQ`) is immutable and device-signed before encryption: device ID/epoch, authority epoch, device event ID, request/revision, Website/Application target and canonical target identity, bounded display evidence/reason, created/pending-expiry timestamps, 32-byte challenge and policy revision.

`SignedApprovalEnvelope` (`GRAP`) binds authority epoch, parent key/sequence, command/nonce/times, device ID/epoch, request/revision, snapshot SHA-256, exact 32-byte challenge, target kind/identity and policy revision. The only decisions are `AllowAlways`, `AllowTemporary`, `AllowDailyQuota`, and `Deny`; temporary/daily duration is 1..1440 minutes and other decisions use zero. Every P-256 P1363 signature is encoded as a length-prefixed `bytes` field whose declared length must equal 64.

`CommandReceipt` records device and authority epochs, parent key/sequence, request/revision, terminal status (`Applied`, `AlreadyResolved`, `Rejected`, `Expired`, `AcceptedPendingReconciliation`), committed policy revision and reconciliation result/detail. `DeviceSignedCommandReceiptEnvelope` (`GRDC`) signs it with a 64-byte P-256 P1363 device signature.

Outer `RelayFrame` (`GRF1`) contains only opaque mailbox ID, recipient key ID, random frame ID, kind, created/expiry, cursor/ack, HPKE encapsulated key and ciphertext; it never reveals a device ID. `EncodeRelayFrameAssociatedData` is exactly the visible metadata and is HPKE AAD. Inner sender signature precedes encryption. Use RFC 9180 HPKE Base mode `DHKEM(P-256, HKDF-SHA256) / HKDF-SHA256 / AES-256-GCM`; encryption and signing keys are separate. This module intentionally implements canonical encoding/hashes, not cryptographic primitives.

Golden deterministic fixtures are in `protocol/test-vectors/relay-v1.json` and `.hex`; no real credentials are present.

## Native enrollment transcript (QR v2)

Windows device identity is now persisted before the first authoritative state by the existing explicit service bootstrap. `device.identity` is a bounded immutable DPAPI CurrentUser record under LocalSystem, with purpose `guard-v2-device-identity-v1`, separate from state/journal. Its internal `GDK1` plaintext is three length-prefixed fields (big-endian i32): canonical ASCII device ID, P-256 signing PKCS#8, P-256 encryption PKCS#8. The public fingerprints use the existing `p256:` SPKI convention; the two keys must differ. Plaintext/temporary PKCS#8 buffers are cleared after use. This is software key storage, not a TPM or non-exportable-key claim.

The authoritative writer lease covers bootstrap; service-only directory/file ACL checks cover both the final and `.pending` path. Only ciphertext is flushed to a create-new pending file and renamed without overwrite. Normal startup never generates/replaces keys; it checks device identity and any saved enrollment's two public keys/roles before publishing IPC. A fully published identity with no state/backup/journal permits explicit first-bootstrap resumption using the same keys. Partial pending files, wrong purpose/format, missing keys for existing state, or substituted identities require explicit recovery. Old lab state without this record is not automatically migrated. Restore of all local files together remains the existing offline rollback limitation; actual SYSTEM/VM power-cut/ACL evidence and Recovery Kit are still gates. Local tests use real temporary files and the test user's DPAPI, not a host service or live policy.

Public deployment authority is compiled into Guard.Service as exactly three `Guard.Enrollment.*` assembly metadata entries: `RelayOrigin`, `AndroidSignerSha256`, `MinimumAndroidVersion`. The corresponding MSBuild properties are `GuardRelayOrigin`, `GuardAndroidSignerSha256`, `GuardMinimumAndroidVersion`; all three must be provided together. Never pass credentials as MSBuild properties. The origin must be an exact canonical lowercase HTTPS DNS authority, with no path, explicit port or trailing slash. Signer is the SHA256 of the trusted Android release signing certificate, not an APK-file digest; version is a positive JS-safe integer. Missing, duplicate, unknown or malformed metadata refuses enrollment. No runtime environment, appsettings, phone or relay fallback exists. Current ordinary builds deliberately contain no release profile; no real APK release key or endpoint was selected by this code change.

`device.relay`/`.pending` use the same immutable protected-file publication and SYSTEM-only boundary as the identity, with a distinct DPAPI purpose `guard-v2-device-relay-configuration-v1`. Its plaintext is bounded 4096-byte strict JSON with exactly `version:1`, `role:"device"`, `relayOrigin`, `deviceId`, `signingKeyId`, `encryptionKeyId`, `mailboxId`, positive `deviceEpoch`/`authorityEpoch`, `accessToken`, and Unix-millisecond `issuedAt`/`expiresAt`. Origin/keys/device must match the trusted build and existing identity, and any saved offer must also match mailbox/epochs. Internal import reads current pristine state through the held writer boundary and permits only initial epochs 1, before setup/IPC; no overwrite or automatic credential rotation. The trusted off-PC provisioning workflow must supply only a device-scoped token, never an admin/bootstrap token. A JSON role label does not prove an opaque token's actual server role: the relay separately enforces the owning-device role when opening an enrollment transport session. That workflow and a secure installer import entry remain to be connected; there is no child/phone/relay import route or plaintext profile file created here.

The off-PC `tools/Guard.Provisioning` operator now persists an immutable issuance job with a fixed, separate DPAPI CurrentUser purpose and user-only ACL before network access. It independently checks the release origin and the exact public descriptor SHA-256, validates both distinct P-256 SPKI fingerprints and initial epochs, then generates a random 256-bit device credential. `publish` reopens the same protected job and uses only `/tokens/initial`; it never falls back to the admin upsert. The admin credential is interactive/memory-only, never included in the job/device profile. The actual trusted descriptor export UI, mailbox bootstrap/deployment, installer and phone acceptance remain open; this CLI does not authenticate an arbitrary descriptor by hashing it.

The transferable installer envelope is **GDI1**: ASCII magic (4), SHA-256 of the exact recipient SPKI (32), HPKE encapsulated P-256 point (65), and AES-GCM ciphertext/tag (plaintext 1..4096 bytes, tag 16). Maximum size 4213 bytes. Reuse the existing RFC 9180 suite; the first 36 bytes are AAD and ASCII `Guard.v2.device-relay.install.hpke.v1` is HPKE info. This encrypts only the existing strict device profile. It does NOT authenticate its sender or confer enrollment authority. The trusted SYSTEM installer stages only this selected file under the existing SYSTEM-only fixed `.install`/`.pending` paths. Explicit service import, before IPC under the writer lease, opens it with the persistent device decryption key and checks compiled origin, both key IDs, device ID, epochs, lifetime and current pristine state before publishing immutable LocalSystem-DPAPI configuration. It consumes staging only after commit; an interrupted exact retry compares the full plaintext without overwriting. Wrong-device/tampered/oversized or old DPAPI-staging inputs refuse; no compatibility fallback. Service identity/configuration DPAPI purposes and normal SYSTEM guards are unchanged.

`ServiceNativeEnrollment.OpenAsync` composes persistent device keys, protected configuration, compiled release pins, real Google roots/status, the durable coordinator and outbound HTTP. Offer creation uses those device keys/mailbox/epochs, a five-minute canonical timestamp window and sufficient remaining credential lifetime for query retention. Composition alone does not open IPC, publish a QR, contact Google/relay, confirm a parent or enable protection. The transcript and Windows/Android/Worker HTTP adapters are implemented, **not yet connected through installer/startup and setup UI**. The old Android `GREN`/QR v1 parser is removed. Reuse the binary rules above, with new magic and binary version 1:

| Magic | Exact field order after version |
|---|---|
| `GREO` | relayEndpoint:text(256), enrollmentId:id, deviceId:id, deviceLabel:text(96), deviceEpoch:positive i64, authorityEpoch:positive i64, mailboxId:id, deviceSigningKeyId:id, signingPublicSec1:65 fixed bytes, deviceEncryptionKeyId:id, encryptionPublicSec1:65 fixed bytes, created:i64, expiry:i64, independentChallenge:32 fixed bytes |
| `GREC` | offerHash:32 fixed bytes, approvalKeyId:id, approvalSpki:91 fixed bytes, parentEncryptionKeyId:id, parentEncryptionPublicSec1:65 fixed bytes |

The offer is at most 1536 bytes, the claim at most 460. Times are nonnegative Unix milliseconds, `created < expiry <= created + 10 minutes`. Native scan and Windows verification reject `now < created` and `now >= expiry`. Relay is an exactly pinned canonical lowercase HTTPS DNS endpoint, no credentials/port/query/fragment/encoded or dot-segment path; each optional path segment contains only lowercase ASCII letters, digits, `_` or `-`. No endpoint normalization or relay-provided trust is allowed. Codecs check key encodings; native curve import and attestation, not successful parsing, establish usable keys. Candidate verification requires four distinct public keys and IDs; approval ID must equal the existing `ParentTrustAnchor` fingerprint (`p256:` + unpadded base64url SHA256 of canonical SPKI).

QR text is exactly `guard-enroll://v2?offer=<base64url GREO>&secret=<base64url 32-byte random setup secret>`, unpadded canonical base64url, at most 2200 characters. Render/scan only in native setup, never navigate, log or send the QR to relay/PWA. The public challenge is independently random, NOT the secret or its SHA256; both obvious reuse errors are rejected. Android owns a private copied secret buffer and clears it on close; the scanner/UI must also discard the original QR string. No secret appears in `GREO` or `GREC`.

`offerHash = SHA256(GREO)` is the Android key-attestation challenge, known before key generation. `claimHash = SHA256(GREC)` binds that offer and both parent keys; sign it with the attested approval key after fresh strong biometrics (ECDSA P-256/SHA256, 64-byte P1363). QR possession uses the existing SYSTEM-held `SHA256(setup secret)` as the **secret authentication key**, not a public verifier: `HMAC-SHA256(key, ASCII("guard-enrollment-possession-v1") || claimHash)`, full 32-byte output. Never publish/store this key outside the protected setup state. Use platform [HMAC](https://www.rfc-editor.org/rfc/rfc2104.html); [Android attestation](https://developer.android.com/privacy-and-security/security-key-attestation) is checked separately off-phone, with trusted roots/status. `VerifyEnrollmentCandidate` computes these digests itself against the locally trusted offer and checks MAC, key roles/points, signature and chain.

**A valid candidate does not authorize ownership.** Someone with a live photographed QR and another valid phone can produce one. `NativeEnrollmentCoordinator` now persists the ceremony and owner in the existing protected authoritative file/journal (schema 2), with these transitions:

1. `BeginAsync` accepts only the authenticated elevated setup role and a locally constructed offer. It generates independent 32-byte QR and local-confirmation secrets. Only their hashes enter protected state; the original setup session receives the disposable QR/local secret. The local secret must never reach the QR, relay, PWA or logs.
2. `StageAsync` verifies the bounded immutable claim/chain/signature/MAC against the saved offer and separately trusted roots/status. The first valid claim is pinned, **not enrolled**; an exact duplicate is idempotent, a different phone conflicts. It persists an HPKE challenge for the claimed decryption key. Send only `claimHash`, 65-byte encapsulated key and 48-byte ciphertext to the phone, never the expected response or entire state object.
3. The phone decrypts a random 32-byte witness using the existing HPKE Base fixed suite. AAD is `claimHash`; info is `ASCII("guard-enrollment-decryption-hpke-v1") || claimHash`. Its response is `HMAC-SHA256(witness, ASCII("guard-enrollment-decryption-proof-v1") || claimHash)`. `ConfirmPhoneKeyAsync` compares the full saved response and marks key possession, not ownership; the phone clears the witness after use.
4. `ConfirmLocalAsync` additionally requires the original local secret, exact state version and full claim hash confirmed by that session. It rechecks the saved attestation/MAC/signature and trusted status, then CAS-commits one owner plus the complete binding and removes the setup challenge. Time/status/certificate bounds are checked after native crypto; the guarded file commit rechecks before publication, after temporary-file flush. Failure leaves the prior owner/state intact. Cancellation before ownership requires the same originating secret/version; ordinary commits cannot remove/replace a confirmed binding.

The future UI must explicitly compare/confirm that same complete claim with the intended phone. No automatic confirmation of the first reply, silent pending replacement or truncated-code shortcut without a reviewed commitment protocol. Old raw-secret/shape-only `SetupCoordinator.CompleteAsync` now always refuses; it cannot bypass this ceremony. Schema 1 remains readable without reset but its keys are **not promoted to attested native enrollment**. This does not solve offline joint rollback or trusted wall-clock rollback.

Remaining integration gates: select/protect the actual release APK signer and verified deployment endpoint, trusted off-PC device provisioning and installer import/startup wiring, originating setup UI plus real scanner/biometric/Google-chain evidence, Recovery Kit, safe phone-record pruning and PWA view bootstrap. The composed components and durable Android result reconciliation below are locally tested, not a live end-to-end enrollment. PWA keys are not approved by merely adding them to a relay message. No ParentRelay named pipe is exposed.

### Local Windows setup IPC (native ceremony)

Only the existing authenticated elevated `AdminSetup` endpoint accepts these verbs. The client authenticates the SYSTEM-owned pipe against the installed running own-process service, its exact process/path/token; it uses Identification-only impersonation. No ParentRelay endpoint is introduced. Old `BeginSetup` (30) now returns `Unavailable` without minting a legacy raw ticket. New commands do not enable protection or finish Recovery Kit/view enrollment.

Requests use the normal correlated GIPC frame. Native JSON is strict UTF-8, maximum 512 bytes/depth 2, exact fields/no duplicates, `version: 1`. Begin has an empty payload, not `{}`. `confirmationSecret` is canonical standard Base64 of exactly 32 bytes; `claimHash` is all 64 lowercase hex characters of the canonical GREC hash. `expectedVersion` is a nonnegative Int64. Native responses are at most 4096 bytes. Never log raw setup frames, capabilities, QR text or response objects.

| Verb | Request fields besides `version` | Effect / successful response |
| --- | --- | --- |
| 34 `BeginNativeSetup` | Empty payload | Uses compiled release pins, installed device profile/persistent keys and the durable native coordinator. Returns `version`, `enrollmentId`, `expiresAt` (Unix ms), `confirmationSecret`, `phase: relay-pending`. No network or QR yet. |
| 35 `AdvanceNativeSetup` | `confirmationSecret` | Verifies the originating session before any network; provisions exact pending offer, processes one outbound exchange, then rechecks state/time. Returns `version`, `stateVersion`, `enrollmentId`, `expiresAt`, `phase`, nullable `qr` and `claimHash`. |
| 36 `ConfirmNativeSetup` | `confirmationSecret`, `expectedVersion`, `claimHash` | Actual phone-key proof, fresh attestation verification and original session/full-claim/version checks precede owner CAS. Empty Success is only local ownership commit. |
| 37 `CancelNativeSetup` | `confirmationSecret`, `expectedVersion` | Cancels only the originating unconfirmed ceremony at the exact version. Does not remove a confirmed owner. |
| 38 `GetNativeSetupResult` | `enrollmentId`, `claimHash` | Read an already-confirmed exact transcript after the one-shot secret was erased, including after a lost reply/restart. Returns `version`, `stateVersion`, `enrollmentId`, `claimHash`, `phase: confirmed`, `relayPassCompleted`, `recoveryRequired`. Never confirms a pending candidate. |

Before phone confirmation, advance phases are `scan-phone`, `phone-proof`, `compare-phone`, or `restart-required`. Show a QR only from a successful `scan-phone` response after relay provisioning. Once a candidate exists the response hides the QR. `claimHash` is returned only after phone decryption-key proof; the intended phone must display the same **complete** commitment, and the user must explicitly confirm the comparison. Never copy a returned hash into an automatic confirm call or replace it with a short comparison code.

The UI privately retains the capability, enrollment ID and compared claim hash; the capability must not appear in a QR, URL, clipboard, telemetry or browser storage. The service retains the unshown QR only in memory. A service restart preserves the durable ceremony but cannot recreate a missing secret: if the original QR was not retained and no candidate exists, report `restart-required`, allow explicit authorized cancellation, or wait for the original five-minute expiry. A lost initial Begin reply similarly requires expiry/restart of the ceremony, never secret recovery/re-keying in place. Requests with malformed input, a foreign capability, stale version or wrong transcript refuse without replacing keys.

Owner commit erases the confirmation verifier; repeated Confirm/Cancel with that spent capability is forbidden. The original UI reconciles using verb 38 and its exact enrollment/claim commitment. During the existing 24h query retention the result call can perform one outbound relay pass for the phone's final encrypted response. Relay failure does not obscure durable local confirmation: `relayPassCompleted: false` means retry delivery; `true` is only a completed poll/reply pass, **not** proof the phone received it. After retention expiry or a backward-clock inconsistency, `recoveryRequired: true` blocks automatic delivery/restart; retain existing keys for explicit recovery. None of these flags means `Protected` or that Recovery Kit was saved. Service operations have a 25s cancellation budget; the authenticated native client has a 30s total I/O budget, distinct from the 5s read-only-query budget.

Production opens real Google attestation/HTTP adapters lazily, from compiled pins and the fixed protected profile only. Internal test factories/HTTP handlers are not DI registrations, environment/config overrides or IPC input. Tests use actual temporary DPAPI/state files, synthetic CA/phone keys and controlled HTTP: begin/retry/QR gate, role/payload/capability/version denial, restart/cancel, real proof+owner commit, spent-secret rejection and lost-reply/offline result. A live SYSTEM/SCM/phone run, installer/operator UI and release provisioning remain separate acceptance gates.

Normal service startup now also owns `NativeEnrollmentDeliveryWorker`, after boundary initialization and before boundary shutdown. It resumes only an already-confirmed durable native owner within the same 24h retention; pending, legacy-without-native-transcript and out-of-window states cause no network. It uses the same handler/relay gate and skips a busy foreground operation, never reconstructs a setup capability, provisions a channel or confirms a candidate. Poll cadence is 10s idle / 2s after processing, with network/pass-timeout backoff 2/4/8/16/30s capped at 30s; HTTP/body loss retains the exact existing ownership and polls again. Each pass is bounded to 25s. Crossing retention during a poll discards the result without stopping the service. Other storage/identity/integrity failures trigger the existing fatal service exit path, without raw payload/exception logging or policy removal. One-time identity/profile startup flags disable this worker. Hosted lifecycle is sequential; stop cancels and drains delivery before keys/writer resources are released. Controlled-HTTP tests verify a newly constructed handler returns a real device-signed, phone-encrypted confirmed result without the originating window, lost publication acknowledgment, foreground serialization and retention. This is not a real SCM reboot, phone receipt, general approval-command runtime or protection readiness.

The Windows window consumes `NativeSetupSession` over the existing authenticated client. It retains the original capability privately in memory, serializes operations, strictly parses bounded replies and pins the canonical QR/session/deadline. QR possession must not reveal the separate local confirmation capability. `ConfirmComparedAsync` is an explicit user action with the **displayed** full hash/version; polling never calls it. A lost confirmation reply leaves `ConfirmationUnknown`: first query the exact committed transcript; only an explicit negative result followed by a successful original-capability advance can offer a new comparison. An outage never silently retries confirmation or begins another ceremony. Lost cancellation remains `CancellationUnknown`, not a successful cancellation. Before the first successful advance there is no known state version for cancellation: close the window/wait for expiry, never guess a version.

The caller drops old QR text/images on phase change, expiry, background/close and awaits `DisposeAsync` to cancel queued/in-flight work and clear owned capability buffers. Closing does not send remote cancel/revoke. Do not serialize/log snapshots (or keep them as history); managed strings/previously issued snapshots cannot be reliably erased. This in-memory window session does not yet provide process-restart persistence. A new window must not reconstruct a confirmation secret; trusted installer/recovery handling and the actual UI remain required. Session tests cover reply loss before/after commit, stale comparisons, malformed/oversized/duplicate payloads, expiry/clock rollback, close/cancellation and the real service begin/advance/cancel path with temporary protected storage.

### Encrypted native exchange (`GREX`, binary version 1)

Implemented in `NativeEnrollmentExchange` and Android `EnrollmentExchange`/`AndroidEnrollmentCeremony`. Worker queue routes and both client HTTP adapters preserve these bytes; production startup and UI are still open. Existing GRF1 limits/roles/kinds are unchanged. A dedicated envelope may carry the existing maximum 64 KiB certificate chain; do not put it into GRF1's reserved signing-intent kind.

All integers remain big-endian. Header/AAD is exactly 108 bytes: `GREX`, version:u32=1, kind:u32 (1 claim, 2 decryption proof, 3 status query, 4 reply), offerHash:32, claimHash:32, requestNonce:32. The remaining fields are enc:65 fixed SEC1 bytes and ciphertext:bytes (u32 length + data/tag). Total is at most 70 KiB; proof ciphertext is exactly 48 bytes, query ciphertext exactly 16, reply ciphertext at most 237 (whole reply at most 414). Reject trailing/unknown/oversized input before processing.

Use the existing single-shot [RFC 9180 fixed Base suite](https://www.rfc-editor.org/rfc/rfc9180.html#section-6.1), a new ephemeral key for every seal, AAD=header, info=`ASCII("guard-enrollment-exchange-hpke-v1") || header`. Requests encrypt to the device encryption key pinned in GREO; replies encrypt to the verified candidate encryption key. HPKE Base alone authenticates neither owner nor sender: claim authorization still requires attestation + biometric signature + QR MAC + originating local confirmation. Reply authenticity additionally requires the GREO-pinned device signature.

- Claim plaintext: `GREK`, version:u32=1, GREC:bytes(max460), certificateCount:u32(2..8), each certificate:bytes(1..16384; sum<=65536), QR MAC:32 fixed, biometric GREC signature:64 fixed. The exact saved evidence is retried; renewed encryption does not generate a new approval signature/key. Windows invokes the existing coordinator and cannot confirm ownership through this route.
- Proof plaintext: the existing 32-byte phone-key proof. Status-query plaintext is empty. An already committed exact claim or a fresh status query may reconcile a lost final reply after QR expiry; an expired pending ceremony cannot advance.
- Reply plaintext: `GRES`, version:u32=1, outcome:u32 (1 needs phone proof, 2 needs originating local confirmation, 3 enrollment committed), stateVersion:positive i64, issued:i64, expires:i64, keyEnc:bytes, keyCipher:bytes, signature:64 fixed. Only outcome 1 has keyEnc=65/keyCipher=48; others require both empty. Device signature is P-256/SHA256/P1363 over `ASCII("guard-enrollment-result-v1") || replyHeader || GRES-without-signature`. Lifetime <=60 seconds and pending replies also end by offer expiry. Windows rechecks version/time after sealing; Android checks exact offer/claim/nonce, device signature, time, kind and bounded fields. Outcome 3 confirms enrollment, **not protection readiness or an application permission**.

The sender must generate a fresh random 32-byte nonce for each new exchange, persist its association with the exact pending attempt and sealed bytes before HTTP, and consume it atomically with a verified result; never take the expected nonce from a relay response. Android's existing no-backup GEN2 record now does this: exact request retry for one minute, then fresh nonce; after offer expiry/local abandonment only a query. Historical confirmed enrollment revalidates the stored device signature at its saved receipt time and requires the original Keystore keys; it is not current authorization or protection readiness. A relay JSON success, lost response or local abandon must not activate ownership/delete keys. A new query after process death can reconcile from retained offer/claim/keys/capability without rescanning an expired QR, within the relay retention window. See `parent/android/README.md` for migration and retention limits.

The transport-only phone capability is `HMAC-SHA256(proofKey, ASCII("guard-enrollment-relay-capability-v1") || offerHash)`, lowercase hex as a bearer credential. .NET/Kotlin derive identical bytes; neither the secret nor proofKey goes to relay. A device-scoped credential provisions its hash and offer expiry in the existing mailbox; no admin credential on the phone/child PC. New claim/proof accepts only before expiry, status queries for another 24 hours, pending exchange bytes at most two minutes. Exact request-byte retries are idempotent; re-encrypting with the same nonce conflicts. Device reply header must match the request's offer/claim/nonce. See `relay/worker/README.md` for routes, quotas and rejection/capability revocation semantics. Worker HTTP status does not replace signed GRES; local cancellation/expired transport is not ownership revocation.

Windows `NativeEnrollmentRelay` reuses the pinned `HttpRelayTransport` for provisioning and one serialized poll/process/reply pass. It reloads the protected session after awaits, rejects replacement of even the same offer with new setup/confirmation secrets, and never supplies local confirmation. A definitive remote crypto/claim rejection deletes only that request; storage, attestation-source and network failures retain it. Following a lost reply POST/restart, poll again: the relay excludes answered requests, so Windows does not blindly re-encrypt and repost against an already committed nonce. The actual coordinator commits before delivery; an unanswered retry is idempotent. Show the originating session's QR only after provisioning succeeds; HTTP failure must not reset setup. Routes pin origin, mailbox, device recipient, complete offer hash and reply correlation; streamed limits and the existing absolute timeout apply to both JSON and binary bodies. Real-file/coordinator/attestation tests with controlled HTTP cover both lost-POST outcomes, restart, hostile messages, concurrent calls, expiry and mandatory local confirmation; this is not evidence of production startup or a live phone/relay exchange.

Interop: `test-vectors/enrollment-exchange-v1.properties` contains explicitly PUBLIC TEST-ONLY keys and actual .NET replies from a synthetic attested ceremony. Kotlin tests verify them and write encrypted claim/proof/query to the ignored build folder. Then run `dotnet run --project tests/Guard.Windows.Crypto.Tests -c Release --no-launch-profile -- --verify-android-exchange parent/android/app/build/test-interop/android-enrollment-exchange.txt` for independent decryption/binding. This is not physical biometric evidence or a live relay test.

Synthetic attested-candidate checks live in the existing Windows crypto harness; neither check is physical biometric evidence.

No host policy or real phone key is used.

- P-384: `6D9DB4CE6C5C0B293166D08986E05774A8776CEB525D9E4329520DE12BA4BCC0`.

The current strict verifier still rejects expired legacy factory chains; physical-phone compatibility and authenticated release updates remain gates. No certificate is installed in a Windows trust store.

Status comes only from `https://android.googleapis.com/attestation/status` using normal platform-validated HTTPS, with no redirect/proxy/cookies, 1 MiB streaming limit and 20-second overall deadline. Cache-Control must be unambiguous and explicitly fresh; Date/Age/transfer time reduce its lease per [RFC 9111 §4.2.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2.3), capped at 24 hours. Monotonic elapsed time also limits the process-only cache. Missing/stale/invalid status, redirect, cancellation and network failure never become an empty revocation list or extend an expired cache. A fresh in-memory entry may be reused until its deadline; a new process fetches again. This is not an independent protected wall clock or resistance to an administrator compromising the host TLS trust/configuration.

Read-only reconnect check from the repository: `dotnet run --project tests/Guard.Windows.Crypto.Tests -c Release --no-launch-profile -- --check-google-source`. It loads the actual pinned roots and retrieves/parses real HTTPS status in a clean process; it does not enroll a phone or launch Guard. No account, token, billing project or secret storage is required. Confirmed 2026-09-30. The adapter and two-party coordinator still require production startup with trusted keys/config/release identity, setup UI and physical-phone evidence before M3 acceptance.
