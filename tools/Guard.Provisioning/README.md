# Подготовка подключения Guard с родительского компьютера

Служебная утилита `.NET 10` для первичной настройки ящика, доступа компьютера и активации обмена с привязанным телефоном. **Не запускайте её на детском ПК.** Она не устанавливает Guard, не меняет Windows и не включает защиту. Это пока отдельный операторский шаг, не законченный семейный мастер установки.

## Что нужно заранее

- Проверенный HTTPS origin своего Guard relay, совпадающий с публичными pins выпуска. Не брать новый адрес из чужого QR/JSON.
- Для нового mailbox — обновлённый Guard relay и отдельно настроенный `BOOTSTRAP_ADMIN_TOKEN`, сохранённый в Bitwarden. Это не API-токен Cloudflare. Утилита не меняет секреты Cloudflare; фактическая настройка этого секрета ещё не выполнена.
- Отдельный случайный пароль администратора ящика (от 32 печатных ASCII-символов), сначала созданный и сохранённый в Bitwarden. Он не должен совпадать с bootstrap secret. Либо уже действующий mailbox и его административный токен, если используется прежняя команда `publish`.
- Публичное описание компьютера от `GetDeviceProvisioning` (33) и независимо проверенный SHA-256 его точных UTF-8 байтов. [Guard.Setup](../../src/Guard.Setup/README.md) получает его через проверенный SCM/SYSTEM pipe, сохраняет файл и показывает полный SHA-256. Сам по себе произвольный JSON или его хеш не доказывает, что это нужный компьютер. Окно ещё требует проверки в VM вместе с доверенным установщиком.
- Существующая приватная папка вне Git на родительском ПК. Файлы создаются без перезаписи, сразу с ACL только текущего пользователя. Утилита отказывает для перенаправленных путей/reparse points и путей внутри Git.

## Команды

Собрать: `dotnet build tools/Guard.Provisioning/Guard.Provisioning.csproj -c Release`.

### Сначала ящик

```text
Guard.Provisioning.exe prepare-mailbox https://<проверенный-relay> <новый-mailboxId> C:\GuardOperator\mailbox.job
Guard.Provisioning.exe publish-mailbox https://<тот-же-проверенный-relay> C:\GuardOperator\mailbox.job
```

Идентификатор ящика — новый уникальный ASCII ID длиной 16–128 символов (`A-Z a-z 0-9 . _ : -`), не `guard:bff:auth:v1`. `prepare-mailbox` скрыто запрашивает пароль ящика из Bitwarden и сохраняет неизменное задание через отдельный DPAPI purpose, без сети. Файл приватен для текущего Windows-пользователя и не заменяет master copy в Bitwarden. Не переносите его на детский ПК, в Git или облачную папку.

`publish-mailbox` скрыто запрашивает **другой** секрет — `BOOTSTRAP_ADMIN_TOKEN`, обращается только к закреплённому origin и проверяет точный ответ `201 {role: "admin", expiresAt}`. Bootstrap secret не сохраняется. После обрыва повторяйте команду с тем же заданием: сервер возвращает прежний результат только для первоначального ещё действующего admin credential, без продления и восстановления отозванного доступа. Конфликт останавливает операцию; обхода через обновление токена нет. Старый ящик без нового bootstrap-маркера не захватывается, даже когда все его токены истекли: используйте предусмотренное восстановление существующего доступа, не создавайте замену семейной установке автоматически.

Начальный административный токен действует год с первой серверной выдачи; повтор не сдвигает дату. Это доступ операторской утилиты, **не срок работы установленного Guard** и не срок API-токена Cloudflare. Ротация рабочего доступа относится к M8. После подтверждённой первичной настройки глобальный bootstrap secret следует отключить в Guard Worker; после отключения bootstrap-повтор недоступен, но выданный mailbox credential остаётся действующим. Этот шаг не выполняется утилитой автоматически.

### Затем конкретный компьютер

Ни один секрет не передаётся аргументом. Ниже названия и адрес — заполнители, срок выбирается явно в UTC; для начала привязки должно оставаться больше суток и пяти минут.

```text
Guard.Provisioning.exe prepare https://<проверенный-relay> C:\GuardOperator\device.json <проверенный-SHA256> <mailboxId> 2027-10-01T00:00:00Z C:\GuardOperator\computer.job
Guard.Provisioning.exe publish-with-mailbox https://<тот-же-проверенный-relay> C:\GuardOperator\computer.job C:\GuardOperator\mailbox.job C:\GuardOperator\computer.profile
```

`publish-with-mailbox` читает приватное задание ящика и **до сети** сопоставляет origin и mailbox обоих заданий. Административный ключ используется только для этого ящика и никогда не включается в профиль компьютера. Для заранее подготовленного администраторского доступа остаётся команда `publish <origin> <computer.job> <computer.profile>` со скрытым ручным вводом.

`prepare` проверяет точную схему, origin, fingerprint и форму обоих различных P-256 ключей, начальные epochs и срок. Генерирует независимый 256-bit device credential и сохраняет неизменное задание через DPAPI CurrentUser с отдельным purpose. Сети на этом шаге нет. Задание открывается только тем же пользователем Windows; храните исходный файл и резервную копию родительского профиля. Не переносите `.job` на детский ПК и не добавляйте его в Git даже в зашифрованном виде.

`publish` запрашивает административный токен в скрытом консольном вводе (можно вставить, Enter — отправить, Esc — отменить). Токен не сохраняется в задании/профиле и не выводится в ошибках. HTTP-библиотеке нужна строка в памяти, поэтому гарантии стирания всех управляемых копий нет; запускайте только в доверенной родительской сессии, без записи ввода/дампов процесса. Master copy остаётся в менеджере паролей.

Утилита отправляет только `POST /v1/mailboxes/{id}/tokens/initial`, роль `device`, собственный decryption recipient и пустой список публикации. Origin повторно сверяется на каждом запуске; redirects, системный proxy/cookies и fallback на изменяющий права `/tokens` отсутствуют. Общий сетевой deadline — 20 секунд, ответ — максимум 512 байт с точными `role` и `expiresAt`.

Только после проверенного ответа создаётся `.profile`: HPKE-конверт для ключа конкретного компьютера. Никаких открытых токенов или приватных ключей в файле нет. Шифрование **не подтверждает отправителя**: доверенный установщик должен сам выбрать правильный файл; запрещён автоматический импорт файлов от ребёнка, телефона или relay.

## Проверка подтверждённой привязки телефона

После фактической привязки окно Guard.Setup может сохранить публичное подписанное подтверждение `guard-native.guard-proof`. На родительском ПК:

```text
Guard.Provisioning.exe verify-native https://<тот-же-проверенный-relay> C:\GuardOperator\computer.job C:\GuardOperator\guard-native.guard-proof
```

Используется именно **исходное** приватное задание компьютера, созданное до привязки. Подпись сверяется с сохранённым тогда ключом, дополнительно проверяются origin, mailbox, оба ключа компьютера, точный offer/claim, эпохи и срок. Подставлять ключ из самого файла вместо исходного задания нельзя. Секреты не вводятся; HTTP, изменение прав и запись задания отсутствуют.

Подтверждение действует максимум десять минут и только в течение суток после окончания исходного QR. Если срок истёк, сохраните новое подтверждение через окно настройки; не сбрасывайте владельца и не заменяйте исходное задание. Несогласованные часы вызывают отказ, а не автоматическую поправку. После окончания суточного окна нужен предусмотренный маршрут восстановления, а не новая привязка ребёнком.

Это проверка подписанного состояния службы, **не активация телефона и не подтверждение включённой защиты**. Не отправляйте admin credential на детский ПК/телефон и не используйте ручной `/tokens` как обход.

## Активация обмена с привязанным телефоном — пока только локальный код

**В действующем облачном Worker новый маршрут ещё не опубликован.** Эти команды — следующий операторский этап, не законченный мастер для семьи. Выполнять на реальном relay следует только после согласованного rollout и готовой защищённой передачи доступа телефону.

```text
Guard.Provisioning.exe prepare-native https://<тот-же-проверенный-relay> C:\GuardOperator\computer.job C:\GuardOperator\guard-native.guard-proof C:\GuardOperator\native.job
Guard.Provisioning.exe activate-native https://<тот-же-проверенный-relay> C:\GuardOperator\computer.job C:\GuardOperator\native.job C:\GuardOperator\guard-native.guard-proof C:\GuardOperator\mailbox.job
```

`prepare-native` проверяет GNA1 по исходному заданию компьютера и сохраняет **одно** неизменное задание с независимым случайным 256-bit approval credential. Файл имеет отдельный DPAPI purpose и ACL текущего пользователя, создаётся только вне Git и без перезаписи. Сети нет. Внутри сохранены точные байты будущего запроса, первоначальное подписанное подтверждение и время подготовки; секрет администратора ящика туда не входит. Файл `native.job` содержит рабочие credentials в зашифрованном виде: **не переносите его на телефон/детский ПК**, в облачную папку или Git.

`activate-native` заново читает исходные device/mailbox/native задания, сверяет origin/mailbox/ключи/срок, затем проверяет **действующее** GNA1. Новое подтверждение может иметь более позднюю версию состояния/срок, но offer и claim должны в точности совпасть с сохранёнными; замена телефона или откат версии отказывают. Время проверяется после чтения файлов, непосредственно перед HTTP и после ответа. Старое подтверждение внутри задания аутентифицирует только сохранённое намерение — не заменяет свежую проверку.

Отправляется только `/tokens/activate-native`, тот же исходный device credential, новый approval credential, начальная эпоха 1 и **неизменный первоначальный срок**. Сервер одной транзакцией разрешает публикацию компьютер↔телефон; PWA/view/locator-доступ не выдаётся. Подтверждается только точный `201 {role: "approval", expiresAt}` в рамках прежних ограничений 20 секунд/512 байт. Redirect/404/409/ошибочный или поздний ответ не вызывают fallback, новую выдачу или изменение файлов.

После потери ответа повторите `activate-native` с тем же `native.job`. Если GNA1 истёк, экспортируйте свежий файл для той же привязки и передайте его повтору; **не запускайте заново `prepare-native` и не меняйте токен**. Повтор отправляет прежние байты, сервер не восстанавливает отозванные/изменённые права. Ни одна из команд не перезаписывает исходные задания и не продлевает credentials. За пределами суточного окна GNA1 требуется маршрут восстановления, не сброс владельца.

Успех означает только подтверждение транспортных прав relay. `activate-native` сама ничего на телефон не передаёт и не доказывает применение защиты Windows.

### Зашифрованный профиль телефона

```text
Guard.Provisioning.exe export-native https://<тот-же-проверенный-relay> C:\GuardOperator\computer.job C:\GuardOperator\native.job C:\GuardOperator\guard-native.guard-proof C:\GuardOperator\mailbox.job C:\GuardOperator\phone.guard-native
```

`export-native` выполняет ту же безопасную активацию/точный повтор с действующим GNA1. Только после проверенного ответа создаёт новый файл, зашифрованный для существующего decryption key привязанного телефона, и показывает полный SHA-256. Внутри только approval credential и первоначальные даты из `native.job`; device/admin credential и приватных ключей нет. Повтор в новый файл может дать другой шифротекст/SHA-256, но не новый credential, срок или права. Существующий файл не заменяется; сетевой отказ/непонятный ответ ничего не экспортируют.

Для переноса предназначен только `.guard-native`, **не `.job`**. HPKE скрывает содержимое, но не удостоверяет отправителя: контрольную сумму на телефоне нужно получать независимо с экрана доверенного родительского инструмента, не из самого файла, relay, письма с файлом или поля, автоматически заполненного импортёром. Профиль не создаёт доверие: Android обязан уже иметь локально проверенный подписанный результат привязки и оба прежних Keystore-ключа.

В Android реализован проверяющий import/storage API: точные GREO/GREC, размер, независимый SHA-256, существующий ключ, срок; на диск попадает только шифротекст в `noBackupFilesDir/native-transport`. Точный повтор без записи допустим, другой credential/срок, повреждение или утрата ключа требуют восстановления, не автоматической замены. **Экран выбора файла и независимого подтверждения SHA-256 ещё не подключён**, как и рабочий approval runtime. До этого live rollout/семейный запуск не проводить; реальный телефон не проверен.

## Сбой и повтор

- Обрыв сети/непонятный ответ: сохраните `.job`, повторите ту же `publish` или `activate-native` команду с исходными файлами и origin. Для активации нужен свежий GNA1. Не генерируйте новый токен. Сервер либо подтвердит прежнюю первоначальную выдачу, либо остановит повтор без изменения последующих прав.
- 404 старого сервера, конфликт после изменения прав/отзыва, неправильный ответ: нет обхода через `/tokens`. Требуется проверка выпуска/состояния оператором; сообщение об ошибке не является доказательством отсутствия серверной записи.
- Уже существует выходной `.profile`: он не перезаписывается. При необходимости точного повторного экспорта укажите новый файл; исходный credential и внутренний профиль останутся прежними, шифротекст может отличаться.
- Повреждённый/недописанный `.job`, чужой Windows-пользователь или расширенные права файла: чтение отказывает. Автоматической регенерации и сброса нет. Файл после ошибки записи сохраняется для диагностики.
- Просроченный credential не продлевается автоматически. Ротация/восстановление действующей установки — отдельный маршрут M8, не повтор первоначальной выдачи.

## Импорт и проверки

Только SYSTEM-часть доверенного установщика атомарно помещает `.profile` в фиксированный `ProgramData\Guard\v2\device.relay.install` под SYSTEM-only ACL, затем использует существующий одноразовый `--import-device-relay-profile`. Служба расшифровывает файл своим ключом, сверяет весь профиль с compiled pins/identity/pristine state и сохраняет прежний LocalSystem-DPAPI `device.relay`. После commit staging удаляется; точный повтор после прерывания не меняет конфигурацию. Старые DPAPI-staging файлы не принимаются: до выпуска контракт заменён переносимым GDI1. Сам установщик и live SYSTEM/SCM проверка ещё не завершены.

Безопасная проверка: `dotnet run --project tests/Guard.Windows.Crypto.Tests -c Release --no-launch-profile`. Используются временные файлы, реальная DPAPI текущего тестового пользователя, реальные ключи/HPKE и контролируемый HTTP handler, затем настоящий service import. Это не проверка живого Cloudflare, UI, SYSTEM ACL или телефона. Создание файла с окончательным ACL использует штатный [FileSystemAclExtensions.Create](https://learn.microsoft.com/en-us/dotnet/api/system.io.filesystemaclextensions.create?view=net-10.0), без новой зависимости.
